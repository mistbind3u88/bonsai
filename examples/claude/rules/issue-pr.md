## Issue・PR の記述

- Issue や PR を書く時は、同じリポジトリで日常的に開発しているメンバーに向けて書く。前提知識はあるが、この問題や変更の経緯は知らない、という読者を想定する
- プロダクトやチーム内で実際に使われている言葉（機能名・画面名・ドメイン用語）を使う。用語に迷ったら既存のコード・ドキュメント・過去の Issue/PR から用例を拾う
- 実装の詳細に踏み込みすぎない。Issue は「利用者・運用者視点で何が起きているか」、PR は「プロダクトとしてどう変わるか／なぜその方針を選んだか」を主軸にする。クラス名・関数名・差分の逐語的な説明は、必要な場合に補足として添える程度にとどめる
- **Issue**: 現状どうなっていて、何が問題で、どうなるべきかを書く。再現手順や影響範囲があれば添える
- **PR**: なぜこの変更が必要で、どういうアプローチを取ったかを書く。コードを読めば分かる「何を変えたか」ではなく、コードからは読み取れない「なぜそう変えたか」を重視する
- 関連する Issue・PR・議論があればリンクする。背景を追えるようにする
- 「いい感じに」「適切に」等の曖昧語を具体的な挙動と範囲に置き換えて書く
- 必要な情報は Issue / PR 本文に直接記載するか、リポジトリにコミットされたファイルを参照する
