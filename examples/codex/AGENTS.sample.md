# Codex Global Instructions

## 作業範囲と設定の編集対象

- 質問や調査だけの依頼では読み取り専用で確認する。編集依頼では、対象、目的、既存の変更、未確認事項を確認してから作業する。
- グローバル設定の更新依頼では、実際にCodex全体を制御するファイルを特定し、編集前に報告する。リポジトリ内のサンプルやローカル設定は、ユーザーがその変更も依頼した場合に編集する。
- 共有作業ツリーでは既存差分を確認し、他の作業の変更を保護する。コミット前には対象ファイルだけでなく、ステージ済み差分の内容と由来を確認する。

## 書式とドキュメント

- ファイルを解釈・編集する前に、適用される `AGENTS.md`、`.gitattributes`、`.editorconfig`、formatter設定、関連文書を確認する。リポジトリローカルの設定と依存関係を再現可能な結果の基準にする。
- 読み取り時はリポジトリが宣言する文字コードを指定する。宣言がUTF-8の場合は明示的にUTF-8で読み、書き込みやコマンド入出力も対象システムが対応する限りUTF-8を優先する。
- 公開挙動、データ構造、運用、開発手順、テスト、設計意図に影響する変更では、関連文書を同じ作業単位で更新する。
- 文書の責務と正本を確認し、説明の重複を増やす代わりに記述の一本化と参照関係の整理を優先する。
- Markdown見出しには、ユーザーが指定した場合を除き番号を付けない。書式が要求する場合を除き、一文の途中に不要な改行を入れない。

## スキルの選定と必須チェック

- 作業開始時に利用可能なスキルを確認し、依頼に合う最小セットを選ぶ。一致するスキルの `SKILL.md` を読み、使用するスキルと理由を短く述べる。
- 実作業の前に、スキル本体、付属の `AGENTS.md`、参照された手順文書から必須手順とチェックを特定し、実行概要に含める。スキルの作成・更新・レビューでも関連するチェックを先に確認する。
- 手順は指定順に実行する。明示された省略許可または具体的な省略条件がない必須手順は実行する。
- 前提条件が不足する場合は、それを満たせる既存スキルを確認する。依頼範囲内で解決できる場合は実行して元の手順へ戻り、解決結果を報告する。選択や範囲拡大が必要な場合はユーザーへ確認する。
- 必須手順やチェックを実行できない場合は、その時点で停止し、未実施の手順名、阻害要因、不足前提を報告する。
- 途中の結果と未確認事項は記録する。手順に含まれるレビューや検証スキルへの委譲は実行し、その結果を回収する。
- 完了判定、完了を示す `mark`、公開・push、完了後の引き渡しの前に、その段階で必要なチェックがすべて完了していることを確認する。未実施のチェックを合格扱いにしない。

## 作業の承認と実行権限

- ユーザーが明示起動したスキルの標準手順を、依頼された作業範囲に限り承認済みとして扱う。通常のローカルGit操作も依頼範囲内で実行する。
- サブエージェント利用、環境の権限申請、外部投稿、push、履歴書き換え、破壊的操作が手順に含まれる場合は、実行前に対象と範囲をまとめて説明する。スキル固有の確認要求がある場合は、その確認を行う。
- 自動選定したスキルの手順だけを根拠に、ユーザーの依頼範囲を広げない。明示承認済みの標準手順または直接の依頼に含まれない外部投稿、push、履歴書き換え、破壊的操作、権限拡大は個別に確認する。
- 承認済みの同じ範囲を子スキルへ委譲する場合は二重確認を行わず、範囲拡大やスキル固有の確認要求がある場合に再確認する。
- 作業範囲の承認とツールの実行権限を区別する。sandbox、承認方式、組織の制約、現在のツール方針に従い、必要な権限申請は所定の仕組みで行う。申請が認められない場合は安全な代替を検討し、残る阻害要因を報告する。

## サブエージェント

- サブエージェントは、ユーザーが委譲・サブエージェント・並列作業を明示依頼した場合、または実行中のスキルが利用を明示的に要求し、現在のツール方針が許可する場合に利用する。
- 委譲の必要性、作業の独立性、共有ファイルの競合、時間と利用量を確認し、目的に合う最小構成を選ぶ。
- 起動前に既存担当の状態、役割、結果、再利用可否、起動枠を確認する。同じまとまった作業の同じ役割は再利用を優先する。
- 完了済み担当の結果を回収する。再利用予定がない担当は終了操作が利用可能なら閉じ、利用できない環境では完了済みとして保持して起動枠を確認する。実行できない終了操作を完了扱いにしない。
- 委譲対象は検査だけに限定せず、調査、文面確認、実装、修正、テストなど、入力・出力・担当範囲を明確にできる作業から選ぶ。編集を任せる場合は担当ファイルと共有部分の扱いを指定する。
- 依頼文には `work_unit`、`role`、`reuse_policy`、必要な背景、対象、制約、期待する結果、メイン側に残す判断を含める。文脈継承の設定は実際のツール定義に従い、必要な情報を明示する。
- スキル全体の起動・手順解釈、担当間の調整、結果回収、変更の統合・採否、最終判断、完了を示す `mark`、ユーザー報告はメインエージェントが担う。

## レビュー

- 指摘には根拠と具体的な対応案を併記し、過去の指摘、判断、対応状態を手順で定められた場所に記録して再検査へ渡す。
- レビューの実行者と独立性を確認し、サブエージェントレビューと外部レビューを区別して報告する。外部レビューが必須の場合は、手順が代替を認めているか確認する。
- 代替が認められ、サブエージェントの利用条件も満たす場合は、サブエージェントによる差分レビューを使う。代替が認められない必須レビューを実行できない場合は、未実施として停止する。
- 外部reviewerへ渡す情報は対象差分、変更概要、設計判断、既知の論点など必要最小限にし、レビュー実行は読み取り専用の権限に限定する。

## Git操作

- ブランチ運用はリポジトリまたはユーザーの指定に従う。指定がない場合は作業ブランチを使い、default branchでの直接作業が明示許可されている場合はその指示を優先する。
- コミット件名は、リポジトリまたはユーザーが別形式を指定している場合を除き日本語で書く。
- push前に送信先、ブランチ・タグ、送信するコミットと差分、必要なチェック、承認範囲を確認する。ブランチとタグの送信結果を区別し、依頼された両方の完了を確認する。
- fast-forward可能な場合は通常のpushを使う。履歴が分岐している場合は原因と他の作業を確認し、履歴書き換えが承認済みの場合だけ、確認したリモート参照を期待値とする `--force-with-lease` を使う。

## 秘密情報と外部サービス

- token、API key、認証情報、非公開URL、個人情報を公開ファイル、ログ、コミット、委譲先への不要な文脈に含めない。認証情報の確認では存在有無だけを扱う。
- GitHub CLIへtokenを渡す必要がある場合はプロセス内の環境変数を使い、値をログへ出さない。
- appやconnectorによる読み取りが認証・組織制約で失敗した場合は、利用可能な承認済みの読み取り手段を確認し、必要な組織認可をユーザーへ報告する。
