# Codex Global Settings Sample

このファイルは Codex グローバル設定向けのサンプルです。コピー先では `AGENTS.md` として配置します。このリポジトリ内では magic filename を避けるため `AGENTS.sample.md` として管理します。

利用時は、`<path-to-skills-repo>`、`<owner/repo>`、`<branch>` などのプレースホルダを自分の環境に合わせて置き換えてください。token、API key、private repository URL、社内ホスト名、個人のホームディレクトリは自分のローカル設定側だけで扱います。

## シンボリックリンクの作成

- Windowsでリポジトリ用のシンボリックリンク（例: `CLAUDE.md -> AGENTS.md`）を作成する場合は、現在のセッションでPowerShellによる作成が可能か先に確認する。
- `New-Item -ItemType SymbolicLink` が管理者権限エラーで失敗した場合は、リポジトリルートから `cmd /c mklink` で再試行し、作成したリンクの参照先を確認する。
- 作成後はシンボリックリンクとして認識されることとGitの状態を確認し、リンク自体が追跡対象になっていることを確かめる。

## リポジトリの書式と文字コード

- ファイルを解釈・編集する前に、`.gitattributes`、`.editorconfig`、formatter設定、`AGENTS.md`、プロジェクト文書など、リポジトリ既定の書式設定と指示を確認して従う。
- 読み取りツールで文字コードを指定する場合は、リポジトリが宣言する文字コードを使う。UTF-8が宣言されている場合は、明示的にUTF-8で読む。
- ファイル編集、生成文書、コミットメッセージ、コマンド入出力では、対象システムが対応する限りUTF-8を優先し、文字コードの混在による文字化けを避ける。
- Prettierをグローバル導入済みの環境では、リポジトリの書式設定と一致する場合に補助として利用する。再現可能な結果の基準は、リポジトリローカルのformatter設定と依存関係に置く。

## Node系コマンドの実行

- Prettierをグローバル導入済みの環境では、`prettier` をそのまま呼び出す。

## Shell scriptの実行

- Windowsでリポジトリのshell scriptを実行する場合は、Gitに同梱された `sh.exe` または互換のPOSIX shell実体を使う。
- script実体とshell実体のパスを確認し、PowerShellへscriptを直接渡す代わりに、確認したshell実体から呼び出す。
- scriptはリポジトリの `tools/` など既定の配置を尊重し、Windows側では `"<path-to-git>/bin/sh.exe" <script-path>` のように外側実行で起動する。
- 報告時は、使用したshell実体のパスと外側実行を使ったことを記載する。

## Skill 利用

- セッション開始時に available skill list を確認し、ユーザー要求、リポジトリ workflow、実行中の手順に合う skill を判断する。
- 複数ステップのタスクやworkflowを始める場合も、実装操作の前にavailable skill listを確認し、該当skillの選定を必須の入口とする。
- 一致する skill がある場合は、その `SKILL.md` を読んでから適用し、どの skill をなぜ使うかを短く述べる。
- 複数の skill が一致する場合は、タスクを満たす最小セットを選び、作業順序に沿って実行する。
- skill の実行中は、`SKILL.md` に書かれた手順を順に実行する。`とばしてよい`、`省略してよい` などの明示がある手順以外は省かない。
- 実行できない手順がある場合は、その手順を未実施のまま止め、阻害要因と不足している前提条件をユーザーへ報告する。明示的な省略許可がないまま黙って先へ進めない。
- skillを明示実行する際は、開始時に `SKILL.md`、付属の `AGENTS.md`、参照された手順文書の必須手順とチェック手順を列挙し、実作業の前に実行概要を提示する。
- skillの実行・作成・更新・レビューでは、関連文書のチェック手順を先に特定し、実行計画に明記する。skillによる明示的な省略許可または具体的な省略条件がないチェックは省かない。
- 完了報告前に、必須手順やチェック手順の未実施が残っていないか確認する。残っている場合は停止し、未実施の手順名、阻害要因、不足前提を報告する。
- 必須チェックがすべて終わるまでは、結果の記録、mark、完了報告、push、レビュー依頼、別skillへの引き渡しを行わない。
- 必須チェックを実行できない場合は、その時点で停止し、未実施のチェック名、阻害要因、不足前提を報告する。

## Skill の前提条件

- Skill の実行中に前提条件が満たされていないことが分かった場合は、その前提条件を満たせる既存 skill があるか確認する。
- 既存 skill で解決できる場合は、その skill を実行して前提条件を満たしてから元の skill に戻る。
- 前提条件の解決に使った skill、解決結果、元の skill へ戻った判断をユーザーへ報告する。
- 既存 skill で解決できない場合、または複数の解決方法があり選択が必要な場合は、足りない前提条件と選択肢を具体的に示してユーザーへ確認する。

## 承認が必要な操作

- skill の手順を読んだ時点で、後続にサブエージェント起動、sandbox 外実行、GitHub 投稿、push、force push など承認が必要な操作が含まれることが明らかな場合は、その操作と範囲を実行前にまとめて提示する。
- ユーザーがskillを明示起動し、その標準手順にこれらの操作が含まれる場合は、skillの実行範囲内で承認済みとして扱い、追加承認を求めない。
- 明示起動したskillの標準手順にサブエージェント起動が含まれる場合、起動前の作業概要は情報共有として扱う。skill自身が確認を要求する場合にだけ承認を確認する。
- 実行途中で初めて判明した承認事項は、その時点で追加確認する。
- ユーザーがskillを明示的に起動した場合は、その `SKILL.md` の標準手順に含まれる操作を、依頼された実行範囲に限り承認済みとして扱う。スキルが個別確認を要求する手順では、その確認を行う。
- 明示的な起動がない場合や、標準手順・依頼範囲を超える操作では、必要な承認を個別に確認する。
- 作業範囲の承認は、sandboxや実行環境の許可を解除しない。実行権限は利用中のツール・承認方式に従い、権限不足の場合は阻害要因と不足前提を報告する。
- 親skillのサブエージェント確認・レビュー・委譲手順で承認された計画を子skillが使う場合は、範囲拡大または子skillによる明示的な確認要求がある場合にだけ再確認する。
- 明示起動したskillの標準手順の外にあるsandbox外実行、GitHub投稿、push、force push、破壊的操作は、個別に承認を確認する。

## Skill起動時の承認の既定値

- ユーザーがskillを明示起動した場合は、`SKILL.md` に書かれた標準手順を、そのskillの範囲内で承認済みとして扱う。
- 標準手順にサブエージェント起動、sandbox外実行、GitHub投稿、push、force push、通常のローカルGit操作が含まれる場合は、それらも作業範囲の承認に含める。起動前確認、委譲境界確認、再利用確認などの前提手順は実行する。
- 起動が承認済みの場合、サブエージェントを起動する直前に二重の承認確認を行わず、必要な確認後に進める。事前説明は、skillが確認を要求する場合を除き情報共有として扱う。
- ユーザーがskillを明示起動した場合、または開発作業を明示依頼した場合、その作業に含まれる `git status`、`git diff`、`git add`、`git commit`、`git log`、`git show` などの通常のローカルGit操作は、plugin・connector・CLIのいずれでも承認済みとして扱う。
- この既定承認はskillの標準手順や依頼範囲を超えて適用せず、範囲が広がる場合は追加操作を個別に確認する。

## グローバル設定とローカル設定

- グローバル設定の更新依頼では、実際にCodex全体を制御するグローバル設定ファイルだけを編集する。
- リポジトリローカルの `AGENTS.md`、`CLAUDE.md`、workspace設定を変更する場合は、そのファイルの変更もユーザーが明示依頼していることを確認する。
- 対象が曖昧な場合は、実際のグローバル設定ファイルを特定し、編集前に報告する。

## サブエージェント

- サブエージェントは、ユーザーが委譲・サブエージェント・並列作業を明示依頼した場合、または実行中のskillが利用を明示的に要求し、現在のツール方針が許可する場合にだけ使う。
- 明示起動したskillに基づいて利用が承認されている場合、skill固有の確認要求がなければ、起動前説明は作業範囲の共有として扱う。
- サブエージェントを起動する前に、既存サブエージェントの完了状態、役割、起動上限の余剰、再利用可否を確認する。
- 完了済みサブエージェントがある場合は結果を回収し、同じ `work_unit` で再利用予定がないものは、終了・close操作がある環境では閉じる。終了ツールがない環境では `/subagent-check` の省略条件に従って完了済み担当として保持し、結果回収・再利用判断・起動枠の確認を行う。
- 同じまとまった作業内で同じ役割の再検査を行う場合は、既存サブエージェントの再利用を優先する。
- サブエージェントには、検査、文面確認、想定質問への回答などの限定タスクだけを渡す。
- スキルの起動、手順解釈、結果回収、最終判断、mark、ユーザー報告はメインエージェントが担う。
- サブエージェントへの依頼文には、`work_unit`、`role`、`reuse_policy`、返すべき結果、メインエージェントに残す判断を含める。
- skillがメインエージェントによる起動を指示する場合は、`fork_context` の既定値を `false` とし、明示的に準備した依頼文だけを渡す。skillまたはユーザーが広い会話文脈を明示要求する場合にだけ継承する。

## Review

- review系skillの指摘を報告する際は、所見に具体的な対応案または修正案を併記する。
- このCodex環境では、ユーザーが別の外部reviewerを明示要求し、実際に利用可能な場合を除き、サブエージェントによる差分レビューをcross-reviewの既定の代替とする。
- workflowがcross-reviewを要求し、外部reviewer CLIを利用できない場合は、サブエージェントレビューでその手順を満たす。
- `claude -p` などの外部reviewerが利用可能で、workflowがその利用を具体的に要求する場合は、read-onlyの外部レビューとして使う。
- `claude -p` に渡す内容は、レビュー対象の差分、変更概要、設計判断、既知の論点、読み取り専用の許可に限定する。
- `claude -p` の実行では、読み取り専用の権限だけを許可する。
- review 系 skill のフィードバックループでは、過去の指摘、判断、対応状態を worktree-local な review log に記録し、次回 reviewer へ明示的に渡す。

## GitHub と token

- token 値は secret として扱う。
- token の存在確認が必要な場合は、存在有無だけを確認する。
- GitHub CLI に token を渡す場合は、プロセス内の環境変数として渡し、ログに値が出ないコマンドだけを使う。
- SAML SSO enforcement などで GitHub app / connector が読めない場合は、`gh` CLI で読み取りを試し、必要な organization authorization をユーザーへ報告する。

## PATH と補助コマンド

- このリポジトリの skill が使う補助コマンドは `<path-to-skills-repo>/tools` に集約される前提で扱う。
- shell 設定では `<path-to-skills-repo>/tools` を PATH に追加する。
- skill の `allowed-tools` には skill 内部パスを直接書かず、PATH に載る bare command 名を使う。

例:

```zsh
path=(<path-to-skills-repo>/tools $path)
export PATH
```

POSIX shell では次の形を使う。

```sh
export PATH="<path-to-skills-repo>/tools:$PATH"
```

## Git 操作

- main / master で開発作業を始める前に、作業ブランチを作成または使用する。
- リポジトリまたはユーザーが default branch での直接作業を明示的に許可している場合は、その指示を優先する。
- コミットメッセージのタイトル（subject）は、リポジトリまたはユーザーが別形式を指定している場合を除き日本語で書く。
- force push は、rebase や autosquash などで履歴が実際に diverge した場合に `--force-with-lease` を使う。
- fast-forward 可能な場合は通常の push を使う。
- 承認済みの作業範囲内で履歴を書き換えたことだけを理由に `--force-with-lease` が必要になった場合は、push直前に再承認を求めない。

## Markdown見出し

- ユーザーが明示指定した場合を除き、Markdown見出しに `1.`、`1.1` などの番号を付けない。
- 書式が要求する場合を除き、一文の途中に不要な改行を入れない。

## ドキュメント

- コード変更とドキュメント変更は 1 つの開発単位として扱う。
- 公開挙動、データ schema、運用、開発者 workflow、テスト、設計意図に影響するコード変更では、関連ドキュメントを同じ実装フェーズで更新する。
- 単一リポジトリ内のドキュメントは、役割ごとに責務を分け、同じ説明を複数ファイルへ重複して持ち込まない方向で改善する。
- ドキュメントを更新する際は、既存文書の責務境界を確認し、転記を増やす代わりに参照関係の整理、記述場所の一本化、重複箇所の削除を優先する。
- 1 つの説明が複数文書にまたがる場合は、どの文書を基準にするかを決め、他方では要約または参照にとどめる。
- 変更せずに質問へ回答する場合は、read-only の確認に留める。
- 情報収集と相談の開始時は、目的、前提、未確認事項、論点、選択肢を整理する。
