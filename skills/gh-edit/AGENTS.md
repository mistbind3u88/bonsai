# gh-edit

## 前提ツール

- [git](https://git-scm.com/)
- [gh](https://cli.github.com/) — `brew install gh`

## 責務の境界

- `gh-edit` は、PR / Issue の新規作成、概要欄ソースファイルの作成・更新、GitHub への投稿を担う。
- 概要欄ソースファイルの文面検査はサブエージェントへ限定タスクとして委譲し、起動前確認は `/subagent-check` で行う。
- サブエージェントは文面検査結果を返し、メインエージェントが修正判断、GitHub 投稿、ユーザー報告を担う。
- push 前の品質確認、PR の差分行への意図補足、レビュー準備の最終確認が必要な場合は、次に使うスキルとして `/check`、`/diff-comment`、`/pr-ready` を案内する。

## サブエージェント依頼

概要欄ソースファイルの文面レビュー依頼は [subagent-prompt-template.md](subagent-prompt-template.md) を埋めて作成する。テンプレートの境界確認、適用ルール、PR 事実情報、検査観点、出力形式を削らず、対象 PR/Issue に合わせて具体値で埋める。

## PR概要欄のスタイル

PR概要欄の作成・更新時は `pull_request_template.md` をベースに使う。以下のスタイル規則に従うこと。

### 全般

- テンプレート内の見出し（`# Subject`、`## やったこと` 等）はリテラルな固定文字列であり、置き換えやパラフレーズをしない
- **日本語**で記述する
- **適用ルールを読む**: リポジトリ・グローバル・ユーザー個別の執筆ルールやPRテンプレートが存在する場合は、概要欄レビュー時に必ず参照する
- **変更規模に合わせる**: 小さい変更に大げさな構造を使わない。1〜2文で済むなら見出し構造なしでよい
- **重複を避ける**: 同じ情報をセクション間で繰り返さない。関連リンク先の内容も再説明しない。各セクションは固有の情報だけを書き、他で述べた内容は参照に留める
- **PRの目的と関係することだけを書く**: PRの目的と無関係な一般論、単なる今後の希望、根拠のない制約説明は書かない
- **参照リンクは主題に直結させる**: References / ref / issue / PR として記載するリンクは、PRの主題、対応Issue、スコープ境界、レビュー判断、または実装判断の根拠として本文中で説明できるものに限定する。単に会話中で触れたIssue/PR、同じ期間に対応したPR、作業者が参照しただけのリンクは、主題との関係を説明できる場合だけ記載する

### `# Subject`

- 背景や目的を簡潔に説明する
- 複雑な変更やパフォーマンス改善では原因→解決策→効果の構造で説明する
- 背景の参照先があれば箇条書きで記載する。記載する参照先は、PRの背景・目的・スコープ境界・判断根拠のいずれかとして本文中で説明できるものにする。Issue と PR は性質が異なるため、プレフィックスで区別すること。番号だけでは判別できないため、記載前に `gh issue view` / `gh pr view` で確認する
- PR の merge で close できる Issue は GitHub のクローズキーワードで関連付ける。Issue の性質に応じて使い分ける。close 対象でない参照は `issue:` プレフィックスを使う
- ローカルファイル（`.claude/docs/` 等）を参照しない。GitHub上で読めない情報への依存は避け、必要な内容は本文に直接記載する
  - `- fixes #123 — 説明`（バグ修正で close する Issue）
  - `- closes #123 — 説明`（機能追加・改善で close する Issue）
  - `- resolves #123 — 説明`（議論・検討の結論として close する Issue）
  - `- issue: #123 — 説明`（参照のみの Issue）
  - `- PR: #456 — 説明`
  - `- ref: <URL> — 説明`（Slack スレッド等、Issue/PR 以外の参照先）

### `## やったこと`

各項目は、PR によってプロダクト・挙動・運用がどう変わったか、またはどんな設計判断をしたかを書く。コードに対して何をしたか（どのファイル・関数をどう操作したか）は書かない。

判定は次の問いで行う: **その項目を、diff を見ていない読み手が読んで意味を取れるか。** 取れなければ実装の文章化になっている。

実装の文章化の典型（要修正）:

- ファイル名・関数名・型名が主語または目的語になっている（例: `tanaoroshi.go に ignore オプションを追加`）
- 「追加した／削除した／移動した／切り出した／リネームした」などコード操作の動詞が記述の中心になっている
- diff のハンクを 1 項目ずつなぞっている

書き起こしの起点は diff ではなく目的・変化に置く。各変更について「なぜこの変更が要るのか」「利用者・運用者・呼び出し側にとって何が変わるのか」を先に言語化し、その答えを項目にする。

- 機能追加: `tanaoroshi.go に ignore オプションを追加` → リポジトリごとに棚卸し対象外の Issue/PR を設定できるようにした
- リファクタ: `通知処理を NotifyService に切り出し` → フィードと通知の責務が混在し変更が波及しやすかったため、通知を分離して影響範囲を狭めた

実装詳細は、外部挙動・互換性・運用・レビュー観点に影響する場合だけ補足として添える。細部の実装都合は概要欄ではなく GitHub のコメントやコードコメントに置く。

### `## やってないこと`

- 関連するがこのPRでは対応しないことがあれば、なぜこのPRでやらないのかの意思決定を含めて明記する
- 記載できるのは、関連Issue、レビューコメント、ユーザー指示、差分上の境界から「このPRと隣接しているが意図的に除外した」と説明できる事項だけにする
- なければセクションごと削除する

### `## 確認したこと`

- 変更内容に対して、CIでは自動検証されない確認事項がないか能動的に洗い出す
- 確認すべき項目があれば未チェック状態（`- [ ]`）で列挙する（GraphQLレスポンス、スクリーンショット、SQL実行結果、パフォーマンス比較など）
- ビルド・テスト・lintなどCIで検証される項目は書かない
- なければセクションごと削除する
