# gh-edit サブエージェント依頼テンプレート

以下を埋めて、概要欄ソースファイルの執筆方針レビューとしてサブエージェントへ渡す。

## 境界確認メタ情報

- 実行中のスキル: `/gh-edit`
- 依頼境界: メインエージェントが `/gh-edit` を実行中であり、サブエージェントの役割は指定観点で概要欄ソースファイルの検査結果を返すこと
- メイン側に残す判断: ソースファイルの修正、`gh pr` / `gh issue` の実行、ユーザーへの最終報告
- サブエージェントが行うこと: 概要欄ソースファイルを読み、適用ルールと PR/Issue 事実情報に照らして文面を検査する
- サブエージェントがメイン側に残すこと: スキル実行、ファイル編集、GitHub 投稿、commit、push、ユーザーへの最終判断

## 対象

- 対象種別: `<PR|Issue>`
- 操作種別: `<create|update>`
- 対象番号または URL: `<number-or-url-or-none>`
- 概要欄ソースファイル: `<absolute-source-file-path>`

## 適用ルールとテンプレート

優先順位:

1. ユーザーの明示指示
2. 対象リポジトリの近い階層の `AGENTS.md` / `CLAUDE.md`
3. 対象リポジトリのルート `AGENTS.md` / `CLAUDE.md`
4. グローバルまたはユーザー個別の執筆ルール
5. スキル同梱ルール（`skills/gh-edit/AGENTS.md`）
6. PR/Issue テンプレート

参照するファイル:

- `<repo-rules>`
- `<global-rules-if-any>`
- `<repo-pr-or-issue-template-or-skill-template>`
- `<skills/gh-edit/AGENTS.md>`

## PR 事実情報

PR の場合だけ埋める。Issue の場合は `対象外として OK` と判定する。

- コミット履歴: `<git log --oneline main..HEAD>`
- 差分 stat: `<git diff --stat main..HEAD>`
- 変更ファイル: `<git diff --name-only main..HEAD>`
- 既存 PR 情報: `<gh pr view ... --json title,body,closingIssuesReferences>`
- 関連 Issue 要約: `<issue-title-body-summary-or-none>`
- ユーザーが明示した制約・スコープ外判断・レビュー指摘:
  - `<instruction-or-none>`

## 検査観点

| 観点                         | チェック内容                                                                                                                              |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| PR/Issue スコープとの整合性  | 各記述が差分、コミット、関連 Issue、ユーザー指示のいずれかに根拠を持つか。根拠のない一般論や将来課題の羅列が含まれていないか              |
| Subject の妥当性             | `# Subject` がタイトルの繰り返しや実装手順ではなく、背景・目的・動機を説明しているか                                                      |
| `## やったこと` の意味性     | 実装ファイル名・関数名・内部処理の逐語説明ではなく、変更の意味、意思決定、レビューすべき影響を書いているか                                |
| `## やってないこと` の隣接性 | この PR と隣接する明確な除外判断だけを書いているか。関連 Issue、レビューコメント、ユーザー指示、差分上の境界から根拠を示せるか            |
| 参照リンクの主題整合性       | References / ref / issue / PR のリンクが、主題、対応 Issue、スコープ境界、レビュー判断、実装判断の根拠として本文中で説明できるか          |
| 見出しと内容の整合           | テンプレートの見出しが保持され、各セクションに想定された内容があり、空セクション、重複、漏れ、齟齬がないか                                |
| 読み手を意識した表現         | プロダクト・チームで使われている言葉を使い、曖昧な表現や独自用語・造語を避けているか                                                      |
| スタイル規則                 | `Closes` / `fixes` の使い分け、コミットハッシュのコードブロック化、ローカルファイル参照、確認項目の粒度など、適用ルールに違反していないか |

## 出力形式

観点ごとに `OK` / `要修正` を示す。`要修正` の項目は以下を添える。

- 対象セクション
- 問題の種類（`根拠不足` / `実装寄り` / `無関係` / `重複` / `スタイル違反` など）
- 該当箇所（見出し名や抜粋）
- 修正方針

```text
観点別結果:
  PR/Issue スコープとの整合性: OK
  Subject の妥当性:            要修正
    - 対象セクション: # Subject
      問題の種類: 実装寄り
      該当箇所: ...
      修正方針: PR の目的・背景・利用者に見える変化から書き直す
```

OK 判定時も、`## やったこと` と `## やってないこと` については「PR事実情報と整合」と明示する。観点を横断する自由記述の所感は不要。
