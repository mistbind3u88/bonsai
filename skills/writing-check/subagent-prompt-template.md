# writing-check サブエージェント依頼テンプレート

以下を埋めて、サブエージェントへ渡す。

## 境界確認

- 実行中のスキル: `/writing-check`
- work_unit: `writing-check:<target>`
- role: `writing-check`
- reuse_policy: `prefer-reuse`
- 依頼する役割: 対象テキストの文面品質を観点別に検査する
- サブエージェントが返すもの: 観点別の `OK` / `要修正` / `未確認` と、要修正または未確認時の理由・修正方針
- メインエージェントが担うもの: スキル進行、最終判断、ユーザー報告

## 検査対象

- リポジトリ: `<absolute-repo-path>`
- 対象: `<text-or-file-or-section>`
- ユーザーが明示した前提: `<user-provided-context-or-none>`
- 明示的に参照すべき資料:
  - `<reference-path-url-or-none> — <why-this-reference-matters>`

対象がファイルやセクションなら、そのパスや範囲を読み、対象が会話中の本文ドラフトならその本文自体を対象として読む。読み手、用途、共有範囲、関連差分、Issue / PR、ユーザー指示が明示されていれば判定材料に使い、明示されていない前提は `未確認` として扱う。

各観点では、観点名に対応する情報が本文にあるかを見て判定する。気になる失敗例を新しい観点として増やす前に、既存観点のどの情報不足として扱うべきかを先に判断する。

## 検査観点

| 観点     | この観点で持つべき情報                                                                             | 要修正にする典型                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 読み手   | 誰向けの文面か、その読み手が理解に必要とする前提知識や読み方                                       | 読み手が不明、または読み手に必要な前提を省いたまま書いている                                                   |
| 目的     | 読み手に何を理解、判断、実行、参照してほしいか                                                     | 何のための文面か分からない、読後に何をすべきか定まらない                                                       |
| 根拠     | その記述を支える事実、差分、仕様、指示、観測結果と、その記述との対応関係                           | 断定しているが根拠が示されない、根拠があっても本文の主張と結び付かない                                         |
| 行動表現 | 読み手や実行者が取るべき行動、確認、判断、出力。禁止や否定を書く場合でも、代わりに何をすべきか     | `しない` `対象外` だけで終わる、責務回避の言い回しで実際の行動が分からない                                     |
| 具体性   | 対象範囲、条件、例外、用語定義、判定単位。ルール文なら、何が原則で何が例外か、どの表現に適用するか | 用語が曖昧、例外の適用範囲が読めない、原則と例外の区別が弱い、具体例を足しただけで判定条件がなお不明           |
| 主語     | 誰がその行動、判断、確認、記録を担うか                                                             | 実行主体や責任主体が省かれ、誰の作業か分からない                                                               |
| 粒度     | 読み手の判断に必要な抽象度。要点、意味、制約、確認方法に対して過不足ない分量                       | 実装詳細に寄りすぎる、逆に抽象的すぎて適用できない                                                             |
| 構成     | 原則と例外の並び、段落や箇条書きの分割、前提と結論の順序、1文あたりの情報量、並列関係              | 情報を足す場所が悪く、既存の定義より例示が前に出る、条件や補足が 1文に詰まり、原則・例外・補足の関係が追えない |
| 配置     | その情報をこの文面に置く妥当性。別の文書、別の節、別の観点説明へ分けるべき内容との境界             | ルール本文に運用判断や別ドキュメント向け説明が混ざる、観点定義より個別事例の説明が前面に出る                   |
| 共有範囲 | 想定される共有先に対して開示してよい情報か、伏せるべき情報やローカル事情を含めていないか           | 共有範囲に不適切な秘匿情報、ローカルパス、個人情報、組織内情報を含める                                         |

表現の好みに留まる差分は `OK` として扱う。文面品質以外の不足は、修正対象そのものではなく `未確認` または残る判断として示す。

具体性の判定では、対象リポジトリや対象文書で明示された表記ルールがある場合は、そのルールに従って判定する。

## 出力形式

```text
writing-check:
  対象: <text-or-file-or-section>
  読み手: OK
  目的: 未確認
    - 対象: <section-or-line>
      理由: <読み手に求める判断や行動を判定する前提が不足している>
  根拠: 要修正
    - 対象: <section-or-line>
      問題: <何が読み手の判断を妨げるか>
      修正方針: <どの根拠や説明を加えるか>
  行動表現: OK
  具体性: OK
  主語: OK
  粒度: OK
  構成: OK
  配置: OK
  共有範囲: OK
```

全観点 `OK` の場合も上記形式で明示する。
