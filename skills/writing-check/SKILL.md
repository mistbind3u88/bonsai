# writing-check

エージェントが書き出したテキスト全般を、読み手に伝わる文面になっているか検査し、結果を報告する。

**このスキルは、実行している主体に応じて動作を切り替える。** メインエージェントが実行するときは、読み取り検査だけを `general-purpose` サブエージェントへ依頼する。サブエージェント自身がこのスキルを実行するときは、さらに別のサブエージェントを起動せず、その場で読み取り検査と報告を行う。メインエージェントが新規起動または再利用を判断できない場合は、その不足を報告して停止する。

このスキルは、指定された本文そのものの文面品質を確認する。検査の軸は、本文の読み手、目的、根拠、行動表現、具体性、主語、粒度、構成、配置、共有範囲に置く。各観点では、対象文面がその観点として持つべき情報を十分に含んでいるかを確認する。コード変更に対する関連ドキュメントの追従や整合の確認は、文面品質以外の不足として示す。

対象例:

- PR / Issue本文
- PR diff commentや進捗コメント
- コードコメント、docstring
- README、手順書、設計ドキュメント、運用ドキュメント、Wikiの本文
- AGENTS.md、SKILL.md、テンプレート
- ユーザーへ提示する回答案、報告文、説明文

## 手順

### 1. 対象テキストを特定する

ユーザーが指定したテキスト、ファイル、セクション、ドラフトを対象にする。

ファイルを指定された場合は `Read` で該当箇所を読む。範囲が広い場合は、ユーザーが確認したいセクションや変更箇所を優先する。対象が曖昧な場合は、どの文章を検査するか短く確認する。

### 2. 実行主体を判定する

このスキルを実行している主体がサブエージェントなら、追加のサブエージェントは起動せず、その場で読み取り検査と報告を行う。手順5へ進む。

このスキルを実行している主体がメインエージェントなら、読み取り検査をサブエージェントへ委譲する前提で進む。

### 3. サブエージェントを起動する

サブエージェントへの依頼文案を会話中に提示した上で、メインエージェントが新規起動または再利用の判断を済ませた状態で起動する。依頼文案のメタ情報には `work_unit: writing-check:<target>`、`role: writing-check`、`reuse_policy: prefer-reuse` を含める。新規起動を選んでいれば新しいサブエージェントを起動し、再利用を選んでいれば既存サブエージェントを再利用する。`WAIT` / `ASK_USER` / `FIX_PROMPT` に該当する場合は起動せず、その理由と不足前提を報告して停止する。

`OK` の場合は `general-purpose` サブエージェントを `run_in_background: true` で起動する。`REUSE` の場合は、既存サブエージェントに前回検査から変わった対象、前回指摘への対応、今回確認してほしい補足条件だけを追加依頼する。同期実行にしない。コンソールを占有せず、完了通知を受け取ってから結果を読む。

#### サブエージェントへの依頼文案

依頼文案は、同ディレクトリの [subagent-prompt-template.md](subagent-prompt-template.md) を埋めて作成する。テンプレートの「境界確認」は `/subagent-check` 用の確認にも使い、「検査対象」以降はサブエージェントへ渡す本文として使う。

テンプレートを埋める際は、以下を具体値に置き換える。

- `<absolute-repo-path>`: 現在の作業ディレクトリの絶対パス
- `<text-or-file-or-section>`: ユーザーが指定した検査対象。ファイル、行範囲、本文、ドラフト、対象セクションを具体的に書く
- `<user-provided-context-or-none>`: 読み手、用途、共有範囲、関連差分、関連Issue / PR、補足条件など、ユーザーが明示した前提。なければ `なし`
- `<reference-path-url-or-none>` / `<why-this-reference-matters>`: 明示的に読むべきファイルパス、URL、関連資料と、その参照理由。該当がなければ `なし`

対象がファイルやセクションなら、そのパスや範囲をサブエージェントへ明示し、必要に応じて `Read` で読ませる。対象が会話中の本文ドラフトなら、その本文を依頼文へ含める。

### 4. 結果を受け取る

サブエージェントの完了通知を受けたら出力を読み、手順7の形式でユーザーに報告する。

### 5. 文脈を確認する

必要に応じて、読み手、用途、共有範囲、関連する差分・Issue・PR・ユーザー指示を確認する。文脈が不明でも、分かる範囲で検査し、不足している前提は `未確認` として扱う。

### 6. 検査する

以下の観点で `OK` / `要修正` / `未確認` を判定する。各観点では、観点名に対応する情報が本文にあるかを見て、不足している情報そのものを指摘する。気になる失敗例を新しい観点として増やす前に、既存観点のどの情報不足として扱うべきかを先に判断する。

| 観点     | この観点で持つべき情報                                                                             | 要修正にする典型                                                                                              |
| -------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 読み手   | 誰向けの文面か、その読み手が理解に必要とする前提知識や読み方                                       | 読み手が不明、または読み手に必要な前提を省いたまま書いている                                                  |
| 目的     | 読み手に何を理解、判断、実行、参照してほしいか                                                     | 何のための文面か分からない、読後に何をすべきか定まらない                                                      |
| 根拠     | その記述を支える事実、差分、仕様、指示、観測結果と、その記述との対応関係                           | 断定しているが根拠が示されない、根拠があっても本文の主張と結び付かない                                        |
| 行動表現 | 読み手や実行者が取るべき行動、確認、判断、出力。禁止や否定を書く場合でも、代わりに何をすべきか     | `しない` `対象外` だけで終わる、責務回避の言い回しで実際の行動が分からない                                    |
| 具体性   | 対象範囲、条件、例外、用語定義、判定単位。ルール文なら、何が原則で何が例外か、どの表現に適用するか | 用語が曖昧、例外の適用範囲が読めない、原則と例外の区別が弱い、具体例を足しただけで判定条件がなお不明          |
| 主語     | 誰がその行動、判断、確認、記録を担うか                                                             | 実行主体や責任主体が省かれ、誰の作業か分からない                                                              |
| 粒度     | 読み手の判断に必要な抽象度。要点、意味、制約、確認方法に対して過不足ない分量                       | 実装詳細に寄りすぎる、逆に抽象的すぎて適用できない                                                            |
| 構成     | 原則と例外の並び、段落や箇条書きの分割、前提と結論の順序、1文あたりの情報量、並列関係              | 情報を足す場所が悪く、既存の定義より例示が前に出る、条件や補足が1文に詰まり、原則・例外・補足の関係が追えない |
| 配置     | その情報をこの文面に置く妥当性。別の文書、別の節、別の観点説明へ分けるべき内容との境界             | ルール本文に運用判断や別ドキュメント向け説明が混ざる、観点定義より個別事例の説明が前面に出る                  |
| 共有範囲 | 想定される共有先に対して開示してよい情報か、伏せるべき情報やローカル事情を含めていないか           | 共有範囲に不適切な秘匿情報、ローカルパス、個人情報、組織内情報を含める                                        |

`要修正` では、読み手の理解、判断、実行を妨げる具体的な問題を指摘する。どの観点で何が不足または過剰かを示す。表現の好みに留まる差分は `OK` として扱う。

具体性の確認では、対象範囲、条件、例外、用語定義、判定単位に加えて、対象リポジトリや対象文書で明示された表記ルールがある場合は、そのルールに従って判定する。

### 7. 結果を報告する

次の形式で報告する。

```text
writing-check:
  対象: <text-or-file-or-section>
  読み手: OK
  目的: 未確認
    - 対象: <section-or-line>
      理由: <読み手に求める判断や行動を判定する前提が不足している>
  根拠: 要修正
    - 対象: <section-or-line>
      問題: <何が読み手の判断を妨げるか>
      修正方針: <どの根拠や説明を加えるか>
  行動表現: OK
  具体性: OK
  主語: OK
  粒度: OK
  構成: OK
  配置: OK
  共有範囲: OK
```

全観点 `OK` の場合も、上記形式で対象と各観点の `OK` を明示する。

## 注意

- 出力は、文面品質の観点別判定と修正方針に限定する。
- 観点名だけを見て機械的に判定しない。各観点が本文に要求する情報を確認して判定する。
- 文面品質以外の不足は、未確認事項または残る判断として示す。
- メインエージェントが読み取り検査を委譲するときは、サブエージェントを必ずバックグラウンドで起動する。同期実行にしない。
- 同じ対象の修正後再検査では、`work_unit: writing-check:<target>` / `role: writing-check` の既存サブエージェントを再利用する。
