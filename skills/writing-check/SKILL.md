# writing-check

エージェントが書き出したテキスト全般を、読み手に伝わる文面になっているか検査し、結果を報告する。

**このスキルは、実行している主体に応じて動作を切り替える。** メインエージェントが実行するときは、必要に応じて読み取り検査だけを `general-purpose` サブエージェントへ依頼する。サブエージェント自身がこのスキルを実行するときは、さらに別のサブエージェントを起動せず、その場で読み取り検査と報告を行う。

このスキルは、指定された本文そのものの文面品質を確認する。検査の軸は、本文の読み手、目的、根拠、行動表現、具体性、主語、粒度、構成、配置、共有範囲に置く。コード変更に対する関連ドキュメントの追従や整合の確認は、文面品質以外の不足として示す。

対象例:

- PR / Issue 本文
- PR diff comment や進捗コメント
- コードコメント、docstring
- README、手順書、設計ドキュメント、運用ドキュメント、Wiki の本文
- AGENTS.md、SKILL.md、テンプレート
- ユーザーへ提示する回答案、報告文、説明文

## 手順

### 1. 対象テキストを特定する

ユーザーが指定したテキスト、ファイル、セクション、ドラフトを対象にする。

ファイルを指定された場合は `Read` で該当箇所を読む。範囲が広い場合は、ユーザーが確認したいセクションや変更箇所を優先する。対象が曖昧な場合は、どの文章を検査するか短く確認する。

### 2. 実行主体を判定する

このスキルを実行している主体がサブエージェントなら、追加のサブエージェントは起動せず、その場で読み取り検査と報告を行う。手順 5 へ進む。

このスキルを実行している主体がメインエージェントなら、読み取り検査をサブエージェントへ委譲する前提で進む。

### 3. サブエージェントを起動する

サブエージェントへの依頼文案を会話中に提示した上で、起動前にスキル `/subagent-check` を実行し、既存サブエージェントの完了状態、再利用可否、起動上限の余剰、依頼文の委譲境界を確認する。依頼文案のメタ情報には `work_unit: writing-check:<target>`、`role: writing-check`、`reuse_policy: prefer-reuse` を含める。`subagent-check` が `OK` を返した場合は、サブエージェントを起動する理由、依頼範囲、読み取り検査だけを任せる境界をユーザーに提示する。呼び出し元で同じ起動範囲について事前承認済みの場合は、その承認に基づいて新規起動する。事前承認がない場合は、ユーザーの承認を得てから新規起動する。`REUSE` / `WAIT` / `ASK_USER` / `FIX_PROMPT` の場合はその判定に従う。

`OK` の場合は `general-purpose` サブエージェントを `run_in_background: true` で起動する。`REUSE` の場合は、既存サブエージェントに前回検査から変わった対象、前回指摘への対応、今回確認してほしい補足条件だけを追加依頼する。同期実行にしない。コンソールを占有せず、完了通知を受け取ってから結果を読む。

#### サブエージェントへの依頼文案

依頼文案は、同ディレクトリの [subagent-prompt-template.md](subagent-prompt-template.md) を埋めて作成する。テンプレートの「境界確認」は `/subagent-check` 用の確認にも使い、「検査対象」以降はサブエージェントへ渡す本文として使う。

テンプレートを埋める際は、以下を具体値に置き換える。

- `<absolute-repo-path>`: 現在の作業ディレクトリの絶対パス
- `<text-or-file-or-section>`: ユーザーが指定した検査対象。ファイル、行範囲、本文、ドラフト、対象セクションを具体的に書く
- `<user-provided-context-or-none>`: 読み手、用途、共有範囲、関連差分、関連 Issue / PR、補足条件など、ユーザーが明示した前提。なければ `なし`
- `<reference-path-url-or-none>` / `<why-this-reference-matters>`: 明示的に読むべきファイルパス、URL、関連資料と、その参照理由。該当がなければ `なし`

対象がファイルやセクションなら、そのパスや範囲をサブエージェントへ明示し、必要に応じて `Read` で読ませる。対象が会話中の本文ドラフトなら、その本文を依頼文へ含める。

### 4. 結果を受け取る

サブエージェントの完了通知を受けたら出力を読み、手順 7 の形式でユーザーに報告する。

### 5. 文脈を確認する

必要に応じて、読み手、用途、共有範囲、関連する差分・Issue・PR・ユーザー指示を確認する。文脈が不明でも、分かる範囲で検査し、不足している前提は `未確認` として扱う。

### 6. 検査する

以下の観点で `OK` / `要修正` / `未確認` を判定する。

| 観点     | 判定基準                                                                                                                         |
| -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 読み手   | 誰が読む文章かが想定され、その読み手に必要な前提が示されているか                                                                 |
| 目的     | 読み手に何を理解、判断、実行してほしいかが明確か                                                                                 |
| 根拠     | 事実、差分、Issue、PR、ログ、ユーザー指示など、確認できる根拠に基づくか                                                          |
| 行動表現 | 打ち消し表現、禁止形、責務回避の言い回しを、読み手が取るべき行動、判断、出力、確認対象へ置き換えられるか                         |
| 具体性   | 曖昧語、未定義の略語、内輪語、ジャーゴンを、読み手が理解できる定義、一般的な表現、具体的な対象へ置き換えられるか                 |
| 主語     | 誰が何を判断、実行、確認、記録するかが明確か                                                                                     |
| 粒度     | コードや差分の逐語説明、実装詳細の羅列、過剰な一般論を、読み手の判断に必要な意味、影響、制約、確認方法へ置き換えられるか         |
| 構成     | 見出し、箇条書き、順序、空欄、重複、同語反復、過剰な免責が整理され、読み手が上から順に理解できるか                               |
| 配置     | その文章に書くべき内容か、別の場所へ置くべき内容が混ざる場合は、どこへ置くべきか判断できるか                                     |
| 共有範囲 | 想定される共有範囲に対して、認証情報、秘匿情報、不要なローカルパス、個人情報、組織内情報などを本文に含めるべきか判断できているか |

`要修正` では、読み手の理解、判断、実行を妨げる具体的な問題を指摘する。どの観点で何が不足または過剰かを示す。表現の好みに留まる差分は `OK` として扱う。

日本語文中の英数字の前後には、原則として不要な半角スペースを入れない。複数の英単語からなる表現では、英単語どうしの区切りに必要な半角スペースは維持する。コード、識別子、URL、Markdown 記法、バッククォート内の表記は、その記法や可読性を優先する。

### 7. 結果を報告する

次の形式で報告する。

```text
writing-check:
  対象: <text-or-file-or-section>
  読み手: OK
  目的: 未確認
    - 対象: <section-or-line>
      理由: <読み手に求める判断や行動を判定する前提が不足している>
  根拠: 要修正
    - 対象: <section-or-line>
      問題: <何が読み手の判断を妨げるか>
      修正方針: <どの根拠や説明を加えるか>
  行動表現: OK
  具体性: OK
  主語: OK
  粒度: OK
  構成: OK
  配置: OK
  共有範囲: OK
```

全観点 `OK` の場合も、上記形式で対象と各観点の `OK` を明示する。

## 注意

- 出力は、文面品質の観点別判定と修正方針に限定する。
- 文面品質以外の不足は、未確認事項または残る判断として示す。
- メインエージェントが読み取り検査を委譲するときは、サブエージェントを必ずバックグラウンドで起動する。同期実行にしない。
- 同じ対象の修正後再検査では、`work_unit: writing-check:<target>` / `role: writing-check` の既存サブエージェントを再利用する。
