# wiki-sync

開発内容から LLM Wiki に残すべき知識を判定し、対象リポジトリの wiki schema に従って同期する。

## 引数

```
$ARGUMENTS: <同期したい内容、または確認したい変更範囲（任意）>
```

引数は同期対象の補足として扱う。特定の Issue/PR 情報が必要な場合は `/gh-read` に委譲する。タスクドキュメントの文脈が必要な場合は `/taskdoc-locate` で場所を解決して参照する。

## 目的

LLM Wiki は、将来の LLM が開発時に「何を守るべきか」「現在の実装ではどう適用すべきか」を判断するための永続的な知識層として更新する。コード・README・AGENTS.md・Issue/PR・作業メモの内容は、再掲ではなく判断に使える知識へ蒸留する。

LLM Wiki はエージェントに生成・保守させるが、人間がプロダクトの目的、担うビジネス、設計判断の背景を把握するための中間成果物でもある。人間の読み手が短時間で文脈を掴める体裁になっているかも作成時の確認対象にする。

参考: [karpathy/llm-wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

`/doc-sync` は既存ドキュメントの追従修正を扱う。`/wiki-sync` は、開発で得た知識を設計判断・契約・運用知識として wiki に昇格するかを判定し、必要な場合だけ同期する。

## 手順

### 1. 変更範囲を把握する

```bash
git status -s
git rev-parse --abbrev-ref HEAD
git merge-base main HEAD
git diff --stat <merge-base>..HEAD
git diff --name-only <merge-base>..HEAD
git log --oneline <merge-base>..HEAD
```

既定ブランチが `main` ではない場合は、リポジトリの既定ブランチに読み替える。

未コミット変更がある場合は、未コミット差分も確認対象に含める。

### 2. LLM Wiki の配置と schema を検出する

対象リポジトリの構成・wiki schema・既存運用に従って実行するため、以下を読む。

- ルート `AGENTS.md` / `CLAUDE.md`
- `README.md`
- `**/AGENTS.md` / `**/CLAUDE.md` のうち、LLM Wiki、wiki、知識層、設計判断、運用ルールに言及しているもの
- wiki 候補ディレクトリ配下の schema ファイル

候補ディレクトリに `AGENTS.md` または `CLAUDE.md` がある場合は、それを wiki schema として最優先で読む。

LLM Wiki が見つからない場合は、「このリポジトリには LLM Wiki が定義されていない」と報告して終了する。wiki の初期化や配置決定は、ユーザーが明示的に依頼した別タスクとして扱う。

候補が複数ある場合は、候補パスと判断理由を提示し、ユーザー確認を取る。

### 3. wiki 更新要否を判定する

次のいずれかに該当する場合は、wiki 更新候補として扱う。

- 設計原則が変わる
- データ契約・schema・protocol・互換性が変わる
- deploy / rollback / migration / 運用手順に影響する
- 下流利用者や外部連携に影響する
- 複数コンポーネントをまたぐ判断基準が増える
- 過去の移行・障害・レビューから再利用可能な教訓が得られた

次の内容は、LLM Wiki ではなく適切な場所に置く。

- コードを読めば分かるファイル一覧や関数呼び出しの逐語説明
- 一時的な作業ログ、未整理の調査メモ、会話の転記
- 現行実装と同期できない詳細な手順
- PR/Issue 本文や README / AGENTS.md と同じ内容の再掲
- コード近傍に置くべき局所的な不変条件
- 根拠が不明な一般論や単なる将来希望

開発者や将来の LLM が判断を誤りそうな情報は、コード近傍のコメント、近い階層の `AGENTS.md`、または該当コンポーネントの仕様書に反映する。

更新不要と判断した場合は、理由を明記して終了する。

### 4. 既存ページを確認する

wiki 配下を検索し、既存ページ更新を優先する。

- 同じ判断領域のページがあれば更新する
- 既存ページの記述と新しい事実が矛盾する場合は、古い記述を曖昧に残さず、どちらが現行か分かるように修正する
- 新規ページは、将来の LLM が答えるべき問いがページ単位で明確な場合だけ作成する

親ドキュメントやルート `AGENTS.md` に個別 wiki ページを逐一列挙しない。ページ一覧の重複管理を避け、必要なページは wiki 配下を直接探す前提にする。

### 5. wiki を更新する

対象リポジトリの wiki schema を最優先し、既存ページの構成・文体に合わせて更新する。

`AGENTS.md` は、リポジトリ全体またはディレクトリ単位の現行仕様・開発規約・参照先を置く。LLM Wiki は、複数領域にまたがる設計判断、運用哲学、LLM 向けの蓄積知識を置く。この役割分担に従い、局所的な制約や実装近傍で読むべき情報は近いドキュメントやコードコメントへ反映する。

schema に明示がない場合は、必要に応じて以下を含める。

- 原則
- 理由
- 現行実装への適用
- 確認対象
- 危険な判断
- 追加参照先

更新時は、コード差分の説明ではなく、その差分によって将来の判断基準がどう変わるかを書く。

あわせて、人間の読み手がプロダクトやビジネスの文脈を追えるよう、見出し、導入、用語、前提、参照先を整理する。単に LLM が検索できる断片ではなく、読み手が判断背景を理解できる文章として整える。

メイン側は、wiki の作成・更新時にこの体裁確認を行う。

### 5a. 用語と抽象度を整える

LLM Wiki は実装者、将来の LLM、人間の読み手が判断基準を共有するための文章として書く。本文の主語には、業務上の概念やプロダクト用語を優先して使う。物理カラム名、定数名、関数名、内部ジョブ名などの実装語は、判断に必要な場合に補助的な参照として添える。

用語に迷う場合は、リポジトリ内の既存ドキュメント、Issue / PR、コード上のコメント、外部サービスの公式ドキュメントを確認し、次の優先順位で表現を選ぶ。公式情報を確認した場合は、wiki 本文の参照先または作業報告に確認範囲を残す。

1. 社内・プロダクトで使われている業務用語
2. 外部サービスの公式日本語訳または正式名称
3. 一般の読み手が誤解しにくい説明的な表現

ユーザーから用語の置き換え指示があった場合は、同じ概念が wiki 内や PR 説明で再発する箇所を全体から探し、業務上の概念やプロダクト用語へ統一する。実装名や略称が本文の主語になっている箇所は、利用者向けの表示名、正式サービス名、契約上の状態名、運用上の判断名など、読み手が判断に使える表現へ置き換える。

### 6. 更新後の確認を並行実行する

更新後、2種類のサブエージェント確認を並行して実行する。ユーザーから追加の品質確認が求められた場合は、6c の追加観点確認も実行する。

このスキルはメインエージェントが実行し、サブエージェントには試行回答、schema・体裁・関連ドキュメント整合確認、追加観点確認の限定タスクだけを依頼する。メインエージェントは wiki 更新、確認結果の解釈、追加修正、ユーザー報告を担う。

各サブエージェントへの依頼文案を会話中に提示した上で、起動前にスキル `/subagent-check` を実行し、既存サブエージェントの完了状態、再利用可否、起動上限の余剰、依頼文の委譲境界を確認する。`subagent-check` が `OK` を返した場合は新規起動し、`REUSE` / `WAIT` / `ASK_USER` / `FIX_PROMPT` の場合はその判定に従う。

確認結果を報告する際は、メイン側で行った確認とサブエージェントに委譲した確認を区別して記載する。

#### サブエージェントの役割別に渡す情報

サブエージェントに渡す情報は、期待する役割に合わせて絞る。回答そのものを検証したいエージェントには、回答を導くための補助情報を渡さず、体裁や不足確認を行うエージェントには、判定基準と対象範囲を明示する。

| 役割                                   | 実行条件                 | 依頼文に含める内容                                                                                                                        | 渡さない情報                             | メイン側が下す判断                                                      |
| -------------------------------------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------- |
| 想定質問への試行回答                   | 通常実行                 | シンプルな想定質問、入口になる wiki ページ、回答に使った根拠の提示依頼、wiki から辿れる参照先や回答者が必要と判断した関連コードの確認指示 | 期待回答、判断のヒント、メイン側の解釈   | 回答が意図した判断に届いているか、wiki 更新・再確認要否、ユーザー報告   |
| schema・体裁・関連ドキュメント整合確認 | 通常実行                 | 更新した wiki、対象リポジトリの wiki schema、体裁・読み手・構成の判定基準、必要な関連ドキュメント                                         | メイン側の指摘採否案、更新後の最終構成案 | 指摘の採否、wiki と近いドキュメントの更新判断、再確認要否、ユーザー報告 |
| 追加観点確認                           | ユーザーが追加確認を要求 | 対象 wiki、関連コード、必要な外部調査条件、ユーザーが確認したい問い                                                                       | 前回の結論、期待する答え、メイン側の解釈 | 疑問点や追加調査対象の採否、wiki への反映判断、ユーザーへの確認事項     |

依頼文案は、役割ごとに同ディレクトリのテンプレートを埋めて作成する。テンプレートの「境界確認メタ情報」は `/subagent-check` 用の確認にも使い、「対象」以降はサブエージェントへ渡す本文として使う。

- 想定質問への試行回答: [answer-check-prompt-template.md](answer-check-prompt-template.md)
- schema・体裁・関連ドキュメント整合確認: [presentation-check-prompt-template.md](presentation-check-prompt-template.md)
- 追加観点確認: [additional-check-prompt-template.md](additional-check-prompt-template.md)

#### 6a. 想定質問への回答を確認する

回答確認用のサブエージェントに、将来の LLM が答えるべき想定質問への回答を実際に作成させる。回答には、wiki とコードのどの情報を根拠にしたかを含めさせる。

依頼文案は [answer-check-prompt-template.md](answer-check-prompt-template.md) を埋めて作成する。読むべき wiki は入口になるページだけを指定し、関連コードは wiki から辿れる参照先または回答者が必要と判断した範囲を読ませる。回答には、根拠として使った wiki とコードの情報を含めさせる。

メイン側は、サブエージェントの回答が意図した判断・制約・注意点を含んでいるかを確認する。

確認すること:

- 想定質問に対して、意図した回答になっているか
- 判断に必要な原則・理由・現行実装への適用が回答に含まれているか
- 危険な判断や避けるべき対応が回答に含まれているか
- 回答が wiki とコードを根拠にしているか
- 不足している前提、参照、判断基準がないか

意図した回答が返らない場合は、サブエージェントの回答から不足している知識を特定し、wiki を更新して同じ想定質問を再度投げる。期待する回答が得られるまで、wiki 更新と回答確認を繰り返す。

この確認では、wiki が将来の LLM の回答を意図した方向へ導けるかを検証する。

作業報告にサブエージェント確認を残す場合は、この 6a の「wiki を通して想定質問に期待する回答が得られるか」の確認を主たる確認結果として記載する。最終的な想定質問と回答は、ローカルパスや作業ツリーの個別事情を一般化した形で要約する。6b の schema・体裁・関連ドキュメント整合確認は、wiki の品質担保として補足的に扱う。

#### 6b. wiki schema・体裁・関連ドキュメントの整合を確認する

schema・体裁・関連ドキュメント整合確認用の別サブエージェントに、更新した wiki、対象リポジトリの wiki schema、必要な関連ドキュメントを読ませる。

依頼文案は [presentation-check-prompt-template.md](presentation-check-prompt-template.md) を埋めて作成する。対象リポジトリの wiki schema に沿っているか、人間の読み手がプロダクトやビジネスの文脈を短時間で掴める体裁になっているかを確認させる。

確認すること:

- 対象リポジトリの wiki schema、ページ構成、文体に合っているか
- 見出し、導入、用語、前提、参照先が読み手の理解順に整理されているか
- コード差分の逐語説明ではなく、判断背景・設計意図・運用上の注意点として書かれているか
- README / AGENTS.md / PR本文 / 作業メモの再掲ではなく、wiki として読む価値のある知識へ蒸留されているか
- 局所的な制約や実装近傍で読むべき情報が、近いドキュメントやコードコメントへ反映されているか

体裁や schema への不整合が見つかった場合は、指摘から不足している構成・文脈・参照を特定し、wiki または近いドキュメントを更新して再確認する。

#### 6c. 追加観点確認を行う

ユーザーから「この概念は他にも置き換えるべきか」「疑問点はあるか」「この wiki で本当に答えられるか」のような品質確認の問いが出た場合は、サブエージェントに追加観点確認を依頼する。

追加観点確認では、対象 wiki、関連コード、必要な外部調査条件、ユーザーが確認したい問いを渡し、サブエージェント自身に不足・曖昧さ・追加調査対象を列挙させる。前回の結論、期待する答え、メイン側の解釈は、サブエージェントの回答後にメインエージェントが検証材料として使う。

依頼文案は [additional-check-prompt-template.md](additional-check-prompt-template.md) を埋めて作成する。サブエージェントへ渡す本文には、対象 wiki、関連コード、必要な外部調査条件、ユーザーが確認したい問いを含める。

追加観点確認の結果は、6a の回答確認とは分けて扱う。疑問点や追加調査対象が見つかった場合は、wiki の修正、関連コード・近傍ドキュメントの確認、またはユーザーへの確認事項として整理する。

## 注意

- このスキルは LLM Wiki が既に定義されているリポジトリで使う
- wiki 配置先、ページ命名、ページ構成は対象リポジトリから読み取る
- GitHub 情報が必要な場合は `/gh-read` に委譲する
- タスクドキュメントを参照する場合は `/taskdoc-locate` で場所を解決して参照する
- 通常ドキュメントの追従修正は `/doc-sync` に委譲する
