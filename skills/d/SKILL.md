# d

企画や開発概要を整理するための discussion 開始スキル。まだ答えや実装方針が固まっていないテーマについて、情報収集と対話を通じて論点を明確にする。

`q` が「質問への回答」を担うのに対し、`d` は「何を決めるべきか」「どの選択肢があるか」を整理する。

## 手順

### 1. 議論テーマを特定する

ユーザーの発言から、議論したい対象を特定する。

- 新しく作りたい機能、skill、workflow
- 既存機能や既存 skill の改善案
- Issue / PR / ドキュメント / 会話履歴から生まれた未整理の相談
- 実装前に決めるべき企画、開発方針、作業範囲

対象が曖昧な場合は、暫定解釈を明示して進める。結論が解釈によって大きく変わる場合は、短く質問する。

### 2. 事実・仮説・未確認を分ける

議論の前提を次の3つに分ける。

- 事実: ユーザー発言、既存ファイル、コマンド結果、コミット履歴などで確認できること
- 仮説: 現状から考えられるが、まだ直接確認していないこと
- 未確認: 追加の確認やユーザー判断が必要なこと

仮説を事実として扱わない。未確認のまま提案する場合は、どの前提が未確認かを明示する。

### 3. 必要な read-only 確認を行う

リポジトリ状態や既存資料が議論に必要な場合だけ、read-only の確認を行う。

```bash
git status -s
git log --oneline <range>
git diff --stat <range>
```

ファイル内容の確認が必要な場合は `Read` / `Grep` / `Glob` を使う。

外部情報や GitHub 状態が必要な場合は、このスキル内で取得せず、未確認事項として示す。

### 4. 論点と選択肢を整理する

議論を前に進めるため、以下を整理する。

- 目的: 何を達成したいか
- 背景: なぜ今検討しているか
- 制約: 守るべきルール、既存方針、技術的・運用上の制約
- 論点: 決めるべきこと
- 選択肢: 取り得る方針とトレードオフ
- 推奨: 現時点で妥当な進め方

選択肢は、違いが判断できる粒度で書く。単なる表現違いや実質的に同じ案を増やさない。

### 5. 残る判断を示す

議論後に残る判断、追加確認、実行前に決めるべきことを示す。

このスキルは論点整理までを担い、ファイル編集、Issue 作成、commit、push は対象外とする。

## 出力

議論開始時の出力は、必要に応じて以下の形にする。

```text
議論の目的:
...

分かっていること:
- ...

未確認:
- ...

主要論点:
- ...

選択肢:
- A: ...
- B: ...

残る判断:
- ...
```

単純な相談では見出しを減らしてよい。複雑な相談では、ユーザーが次に判断できる粒度まで分解する。
